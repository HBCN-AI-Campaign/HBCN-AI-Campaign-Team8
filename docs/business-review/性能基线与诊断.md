# 单页扫描件 OCR 性能基线

## 可重复基准

基准脚本只输出阶段耗时、文本/字段/定位计数和结果一致性状态；不会写出 OCR 文本、字段值或业务文件名。样本从 `HBCN_BUSINESS_MATERIALS_ROOT` 指定的共享目录中按套号和单据类型查找，渲染页在结束后自动删除。

PowerShell 示例：

```powershell
$env:HBCN_BUSINESS_MATERIALS_ROOT = 'E:\2026_AgentStudy\Python_code\HBCN_AI_Campaign_Team8_Clever\汇丰竞赛8组共享文件夹\01_汇丰业务文件'
$env:PYTHONPATH = "$PWD\code\backend;$PWD\code\ocr_service"
& '<OCR 虚拟环境>\Scripts\python.exe' docs\business-review\profile_single_pdf_ocr.py `
  --dataset 10 --doc-type PROFORMA_INVOICE --batch-sizes 1,8 --cpu-threads 4
```

需使用含 `pdfplumber`、`paddleocr`、PaddlePaddle 的 OCR 虚拟环境。基准固定按 200 DPI 渲染；不要通过降低 DPI 或跳过识别模块缩短耗时。对照运行串行启动独立子进程，隔离模型初始化和批次状态。

## 本机结果

环境：Windows、CPU-only、PaddleOCR 3.7.0、PaddlePaddle 3.2.1。样本为第十套一页形式发票扫描件，文本层为空，保留生产当前 200 DPI 设置。

| 阶段 | 运行 A：batch=1、CPU threads=4 | 运行 B：batch=8、CPU threads=1 | 说明 |
| --- | ---: | ---: | --- |
| 页面渲染 | 2,986 ms | 共用同一渲染结果 | 渲染质量未改 |
| 模型初始化 | 16,844 ms | 14,999 ms | 两个隔离子进程，缓存已存在 |
| OCR 单页推理 | 130,778 ms / 4 线程 | 112,424 ms / 1 线程 | 1 线程约 1.16 倍 |
| 字段归一 | 1.26 ms | 1.44 ms | 不含原文块查找 |
| 含证据定位的字段映射 | 0.99 ms | 0.85 ms | 3 个有值字段、3 个有定位字段 |
| 原文块定位 | 0.13 ms | 0.14 ms | 3 次查找，共检查 69 个文本块 |
| OCR 输出 | 记录为 54 行、854 字符 | 报告表称摘要一致 | 报告正文另称摘要不一致，原始 JSON 未留存，结论冲突 |
| 业务字段输出 | 记录为 3 个有值、3 个可定位 | 报告表称摘要一致 | 报告正文另称字段摘要不一致，原始 JSON 未留存，结论冲突 |

这两次运行同时改变了 batch 和 CPU 线程数（batch 1 / 4 线程对比 batch 8 / 1 线程），只能作为探索性观察，不能把耗时变化归因于 batch 或线程。报告表与正文对 OCR/字段摘要是否一致的记录也相互冲突，且没有原始 JSON 可复核；因此当前不能确认输出一致性，也不据此改变服务默认配置。这里记录的字段数和耗时不等于识别准确率。

需要受控验证时，固定 CPU 线程只比较 batch：`--batch-sizes 1,8 --cpu-threads 4`；固定 batch 只比较线程数：`--batch-sizes 1 --cpu-threads 1,4`。两组都应在同一样本、机器、DPI 和模型版本下执行并保留 JSON 结果，再分别比较摘要和耗时；未完成该验证前不形成单因素性能结论。

## 瓶颈判断与最小回归

阶段记录显示单页 OCR 推理占据绝大部分耗时；但由于上述参数同时变化且输出记录互相冲突，这些数字只可用于定位待研究方向，不能作为 batch 或线程的因果结论。当前设备没有 CUDA，双进程并行会重复加载约 2 GB 级模型并竞争 CPU/内存；本机不做这种并行尝试。

最小回归使用下列确定性业务断言：

```powershell
cd code\backend
$env:PYTHONPATH = (Get-Location).Path
& '<后端测试虚拟环境>\Scripts\python.exe' -m unittest `
  tests.test_supporting_rules.SupportingRuleTests.test_invoice_above_contract_is_a_hard_failure `
  tests.test_business_review.BusinessReviewApiTests.test_vision_ocr_fields_require_review_before_archive
```

一项断言保证明确金额超限仍触发强规则失败，另一项保证缺少/视觉 OCR 字段不能自动归档。真实性能对照需用上方单页脚本分别执行受控 batch 与线程对比；任何正式默认变更还需独立标注材料复核 OCR 输出。

## 支付指令长请求诊断

三套材料首次限定回放使用后端默认客户端超时 180 秒。第八、九套支付指令请求分别在约 180 秒被后端截断；随后单份串行定向请求确认 OCR 服务可以成功完成：

| 材料 | 接口 | 状态 | 耗时 | OCR 块 | 字段结果 |
| --- | --- | ---: | ---: | ---: | ---: |
| 第八套支付指令 | `/extract` | 200 | 218.9 秒 | 接口不返回 | 5/5 有值 |
| 第八套支付指令 | `/file/detailed` | 200 | 270.9 秒 | 150 | 5/5 有值且可定位 |
| 第九套支付指令 | `/file/detailed` | 200 | 259.7 秒 | 150 | 5/5 有值且可定位，金额字段 1/1 可定位 |

因此首次的两项“空 OCR”应分类为客户端请求超时，而不是空白材料。未改变生产默认超时；限定补测的单次上限设为 600 秒，并串行处理。若要在真实用户流程使用这类 CPU 扫描件，仍需评估异步任务和前端状态查询，不能依赖同步 HTTP 长时间挂起。

首次回放还观察到一次 `/file/detailed` HTTP 500。之后第十套三份材料各做了一次定向明细重放，均返回 200，未能复现该错误；原响应和堆栈未留存，所以具体异常类无法追溯。解析器现以异常类名作为安全诊断字段和日志项，相关单测通过；后续如再出现 500，可由 `error_type` 分类，不记录错误正文或临时路径。

## 方案边界与官方资料

PaddleOCR 官方 OCR 文档列出 `text_recognition_batch_size`（默认 1），并说明其作用于文本识别模块；本轮对照据此设计。官方并行推理说明多设备路径要求多个推理设备，示例的自建多进程主要面向多 GPU；当前机器 CPU-only，不具备该路径。官方高性能推理文档列出的 CPU 支持环境为 Linux x86-64、Python 3.8–3.12；当前 Windows Python 3.13 不能据此直接启用或宣称验证通过。
