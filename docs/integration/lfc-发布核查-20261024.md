### 4 号：规则引擎整批结果被短路（需要模块负责人决策）

诊断复现（同一任务、合同 100 / 发票 90、缺支付指令）只得到 `PARSING_READY` + 若干 `OCR_PARSE_QUALITY_REVIEW`，**所有业务规则结果（含 `SUPPORTING__AMOUNT`）都没有产生**。

根因：`app/rule_engine/runner.py` 的 `run_all()` 在任一单据存在未决识别字段时直接返回单条 `PARSING_READY`，不再执行其余规则。该短路由解析分支提交 `d3f1564（parsing: 接入OCR字段解析与隔离验收）` 引入；业务审核分支的 API 回归 `test_business_review` 写于其之前，期望规则照常运行并把金额链判为 `warn`。

两种口径都成立：解析侧要求“未核实字段不得参与金额判定”，业务侧要求“规则结果要能看到”。当前实现选了“全部不跑”，会让页面在有任一未决字段时失去全部差异结论。**这属于产品口径变更，集成方不擅自改，需业务审核与解析负责人共同定：是保留全短路，还是只短路受影响规则、其余照常输出。**

### 5–7 号：解析重构后的过期测试

`app/parse_agent.py` 在解析分支已重构为 `app/parsing/*` 管线（本次合并净减 453 行），`_find_with_source`、`httpx` 等内部符号不再存在于 `parse_agent` 命名空间。业务审核分支 `0649767` 新增的 `test_parse_agent_single_pass.py` 仍按旧内部 API 打补丁，因此三例报 `AttributeError`。

被覆盖的行为本身仍需要验证（OCR 失败日志不得带响应体/本地路径、无匹配文本块时置信度必须为 0.0）。修复方向是**改测试指向新管线**（如 `app.parsing.providers`），不是删除断言；本轮未改，避免与解析负责人正在推进的实现交叉。

### 1–3 号：依赖缺失，非代码缺陷

`hbcn_assistant` 来自 `code/assistant-sdk`（需 `pip install -e`），`alembic` 来自 `requirements-assistant.txt`。本轮使用的解释器是业务审核工作树的 venv，未安装这两项；换用按 `requirements.txt + requirements-assistant.txt + assistant-sdk` 完整安装的环境即可，**不计入代码缺陷**，但也说明“集成环境的完整依赖清单”尚未固化成一条可复现命令。
